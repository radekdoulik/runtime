    Demonstration of the full IDE-driven async-break flow over CDP. The page
    is a passive runtime host: it loads the CoreCLR runtime + sidecar
    (mscordbi/DAC), exposes a small globalThis.__dbi facade, and
    runs a managed busy loop. All orchestration is driven from the
    IDE/DBI side via CDP Debugger.pause / Debugger.resume
    plus Runtime.evaluate calls into the facade.
  

  

    Flow when a CDP client is attached (Playwright test, Chrome DevTools, or
    any ICorDebug-style debugger speaking CDP):
    
    
      
  1. IDE issues CDP Debugger.pause → V8 freezes the wasm runtime thread.
    2. 
      
  2. DBI writes the runtime's atomic g_wasmDebugAsyncBreakInProgress flag directly into runtime memory (the runtime is frozen so its own setter cannot run; the 1-byte memory write IS the synchronization).
    3. 
      
  3. IDE issues CDP Debugger.resume → V8 unfreezes the runtime.
    4. 
      
  4. The runtime continues until the next INTOP_DEBUG_SEQ_POINT, where the interpreter checks the flag, halts cleanly, populates g_wasmDebugLastIpcAsyncBreak + g_wasmDebugLastLocalsRecord, and calls the JS stop trigger. The libCorerun.js wrapper's debugger; halts V8 again.
    5. 
      
  5. DBI polls the structured event + locals schema via the sidecar DAC (__dbi.pollAsyncBreakEvent / __dbi.pollLocals) — a real DBI/DAC round-trip into the frozen runtime's memory.
    6. 
      
  6. DBI renders the data in the browser via __dbi.renderPausePanel so the user sees the locals.
    7. 
      
  7. DBI holds for 5 seconds (simulating a human staring at the debugger UI).
    8. 
      
  8. IDE issues CDP Debugger.resume → the runtime continues; loop runs to completion.
    9.
